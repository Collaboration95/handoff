HANDOFF V2 — ARCHITECTURE DECISION / MINIMUM-PATH IMPLEMENTATION
Last updated: 2026-09-12

GOAL
Build a convincing hackathon demo without spending time on generic infrastructure.

CORE PRINCIPLE
Do not build video calling, WebRTC, audio transport, recording, speech plumbing, or generic agent orchestration yourself.

Use existing infrastructure for commodity pieces.

Spend custom development time on:
- meeting context understanding
- reference resolution
- intent/tool selection
- real GitHub actions
- real Slack actions
- human-safe approval
- visible action provenance
- one optional deep-work delegation
- one optional sandbox payment-link action through Airwallex Developer MCP

ARCHITECTURE PRINCIPLE
Use a TWO-SPEED agent architecture.

FAST PATH
For immediate, deterministic actions:
- retrieve GitHub item
- assign issue
- request PR review
- send Slack message

Use:
GPT-Live-1
-> delegated/fast OpenAI reasoning
-> narrow direct tool
-> result
-> spoken confirmation

DEEP PATH
For genuinely autonomous work:
- investigate a bug
- inspect a codebase
- run tests
- prepare a patch
- analyze implementation

Use:
GPT-Live-1
-> start_repo_task(...)
-> OpenAI Agents API / coding harness
-> optional GPT-6 Astra if available
-> sandbox / broad repo access
-> progress + result

Do NOT route simple realtime actions through the Agents API.

RECOMMENDED STACK

1. VIDEO / MEETING LAYER
Use LiveKit Meet.

Why:
- open source
- ready-made multi-user video/audio room
- handles microphone, camera, participants, screen sharing, WebRTC, and room management
- can be minimally rebranded
- avoids writing a custom conferencing frontend

Customize only:
- Handoff branding
- small live/listening state
- Agent Activity panel

Do NOT implement:
- WebRTC negotiation
- microphone streaming plumbing
- participant media layout
- recording
- custom video/audio transport

2. REALTIME AGENT
Use LiveKit Agents.

Architecture:

Human participants
    ->
LiveKit Room
    ->
Handoff joins as agent participant
    ->
GPT-Live-1
    ->
spoken output back into LiveKit Room

Why:
- the agent behaves as a participant
- LiveKit handles room audio delivery
- LiveKit handles returned agent audio
- interruption is part of the realtime interaction
- no custom STT/TTS pipeline is needed

3. REALTIME MODEL
Use GPT-Live-1.

Responsibilities:
- listen/speak in realtime
- manage conversational turn-taking
- support interruption/correction
- maintain the natural spoken meeting interaction
- acknowledge deep-task delegation without blocking the meeting

GPT-Live-1 should NOT directly contain all product logic.

4. FAST REASONING / TOOL SELECTION
Use a fast OpenAI Responses-capable model behind the realtime voice layer.

Responsibilities:
- resolve "that", "him", "the fix", etc.
- map speech to structured tool calls
- decide which narrow tool is needed
- decide whether approval is required
- construct useful Slack text
- update important meeting state

Prefer a fast strong model available at the event.
Do not use the most expensive/deepest model for every trivial action.

5. FAST TOOL LAYER
Keep this narrow and deterministic.

GitHub:
- get_github_item(issue_or_pr)
- assign_github_issue(issue, person)
- request_pr_review(pr, person)

Optional:
- create_github_issue(repo, title, description)

Slack:
- send_slack_message(channel_or_user, text)
- send_slack_dm(user, text)

Do NOT expose a giant generic GitHub/Slack surface to the realtime model.

5A. OPTIONAL AIRWALLEX DEVELOPER MCP EXTENSION — STRETCH
Add this only after the core demo is stable and sandbox access is already available.

Expose one narrow action:

create_airwallex_payment_link(invoice_or_amount)

Flow:
GPT-Live-1
-> contextual invoice/amount resolution
-> Airwallex Developer MCP
-> sandbox payment link
-> optional Slack delivery
-> spoken confirmation + Agent Activity event

Keep the integration intentionally tiny. Do not implement production AgentOS, payments infrastructure, cards, payouts, beneficiaries, or additional Airwallex workflows. Treat payment-link creation as a consequential write and use the existing conversational approval model where appropriate.

6. DEEP-WORK AGENT — STRETCH
Add only after the core demo is stable.

Expose a narrow bridge:

start_repo_task(
    repo,
    objective,
    github_context
)

Optional:
get_repo_task_status(task_id)

Internally:
- create/resume an Agents API session
- give the task repository/issue context
- run repository investigation / tests / patch work
- emit status events
- return a concise final result to Handoff

Use case:
"Handoff, investigate why that auth issue is happening."

This is where a durable coding harness is appropriate.

7. GPT-6 ASTRA — OPTIONAL
If GPT-6 Astra API access is available, use it only where its stronger coding/tool ability is visible:

GOOD:
- repository investigation
- multistep debugging
- test execution/reasoning
- patch preparation
- deep coding task

NOT GOOD:
- "assign issue #12"
- "send Alex a Slack message"
- routine realtime confirmations

This keeps latency and complexity low while still showcasing current OpenAI technology.

8. MCP POLICY
Do not adopt MCP merely because it exists.

Realtime critical path:
- prefer direct narrow GitHub/Slack wrappers

Optional sponsor extension:
- use the Airwallex Developer MCP only for one sandbox payment-link action
- do not add a broad finance tool surface to the realtime path

Deep-work path:
- GitHub MCP is reasonable if broad repository/issue/PR access makes the agent implementation easier
- MCP should replace integration boilerplate, not add orchestration complexity

9. MEETING STATE
Use a tiny in-memory state object.

Example:

meeting_state = {
    "current_github_item": None,
    "current_pr": None,
    "current_person": None,
    "current_topic": None,
    "pending_action": None
}

Purpose:
- deterministic contextual references
- reliable corrections
- clean action confirmation

Do NOT add:
- Redis
- vector DB
- long-term memory
- database
unless the hackathon demo absolutely requires it.

10. PEOPLE / IDENTITY MAPPING
Use hardcoded config.

PEOPLE = {
    "Guru": {
        "github": "<github_username>",
        "slack": "<slack_user_id>"
    },
    "Alex": {
        "github": "<github_username>",
        "slack": "<slack_user_id>"
    },
    "Sarah": {
        "github": "<github_username>",
        "slack": "<slack_user_id>"
    }
}

This is sufficient for a hackathon.

11. APPROVAL MODEL
Keep approval conversational.

READ
Execute immediately.

LOW-RISK WRITE
Usually execute immediately for the demo.

CONSEQUENTIAL WRITE
Set pending_action and ask for a quick spoken confirmation.

For the optional Airwallex extension, creating a sandbox payment link is still treated as a consequential write even though it is not a production charge.

Example:

Handoff:
"I'm ready to assign issue 12 to Sarah. Go ahead?"

User:
"Actually, assign it to me."

Handoff:
updates pending_action

User:
"Yes."

Handoff:
executes the corrected action

No approval dashboard is needed.

Use LiveKit data messages for small application events.

Suggested event types:

context_resolved
action_proposed
approval_requested
approval_received
action_started
action_completed
action_failed
deep_task_started
deep_task_progress
deep_task_completed

Example:

{
  "type": "context_resolved",
  "reference": "that",
  "resolved_to": "GitHub #12"
}

{
  "type": "action_completed",
  "service": "github",
  "action": "assigned_issue",
  "target": "#12",
  "person": "Guru"
}

{
  "type": "deep_task_progress",
  "task_id": "task_123",
  "message": "Running authentication tests"
}

14. SLACK STRATEGY
Slack is an action destination, not an input surface.

Use:
- one free Slack workspace
- one app/bot
- one or two channels
- current user DM

Do NOT implement:
- Slack event subscriptions
- mentions
- slash commands
- Socket Mode
- incoming Slack conversation
- complex OAuth
- multiple workspaces

15. GITHUB STRATEGY
Use one dedicated demo repository with predictable fixtures.

Recommended:
- Issue #12: authentication timeout bug
- Issue #42: retry / HTTP 429 issue
- PR #18: authentication fix

Ensure before judging:
- issue numbers exist
- PR is open
- user can be assigned
- reviewer request is allowed
- labels/descriptions are stable
- demo can be reset quickly

16. RECORDING
Do not implement meeting recording.

For submission:
- use macOS screen recording, OBS, or equivalent external recorder

Capture:
- meeting UI
- Handoff speaking
- interruption
- Agent Activity panel
- GitHub side effect
- Slack side effect
- optional deep task

19. HANDOFF'S ACTUAL PRODUCT RESPONSIBILITY

CONTEXT
Understand references:
- "that issue"
- "the fix"
- "him"
- "what we decided"

INTENT
Map natural speech to structured actions.

CROSS-SYSTEM EXECUTION
Example:
"Get Alex to review it and let him know on Slack."

Actions:
- request GitHub review
- send Slack DM

OPTIONAL FINANCE EXTENSION
Example:
"Create a payment link for that invoice."

Actions:
- resolve the invoice and amount from meeting context
- create one sandbox payment link through Airwallex Developer MCP
- optionally send the link through Slack

REALTIME CORRECTION
Example:
"Actually, not Alex — Sarah."

Update the pending action before execution.

SAFETY
Ask for lightweight confirmation where appropriate.

DELEGATION
Recognize when a request is not a simple side effect but a real task.

Example:
"Investigate the bug."
-> deep task

"Assign the bug."
-> fast tool

FINAL IMPLEMENTATION DIRECTIVE
Fork/use LiveKit Meet.
Run Handoff as a LiveKit Agent participant.
Use GPT-Live-1 for the realtime human conversation.
Use fast OpenAI reasoning for contextual resolution and narrow tool calls.
Keep GitHub and Slack direct and deterministic.
Use hardcoded user mappings.
Keep important context in a tiny in-memory object.
Use conversational pending-action approval.
Publish action events to the meeting UI.
Do not implement recording.
Only after this is stable, add at most ONE optional stretch flow: the Airwallex sandbox payment-link demo or the Agents API deep-work flow.
If the Airwallex extension is selected, keep it to one MCP action and optional Slack delivery.

Handoff's value must come from:

conversation context
-> intent understanding
-> appropriate execution path
-> real action/work
-> human-safe behavior
-> visible confirmation

NOT from infrastructure.
